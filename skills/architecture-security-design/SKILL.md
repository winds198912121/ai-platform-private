# セキュリティ設計（既定で拒否）

## Overview
誰が本人性を確認し、誰が何を行え、各 API がどの資源を扱うかを設計書に具体化します。未記載のセキュリティ規則が実装段階で自然に補われるとは考えません。

## When to Use
- 設計書、API 一覧、権限表、データフロー、外部依存を作成・レビューするとき。
- security-baseline を各 API と資源範囲へ具体化するとき。
- 対象外：ソース脆弱性スキャン、侵入テスト、本番障害対応（operations-incident-response を使用）。

## Core Process
- 各項目を設計書の必須事項とします。
- 認証と認可を分け、セッション / JWT / SSO の期限・更新方式と、ロール→権限→資源範囲の既定拒否の表を記載します。
- 全 API に必要ロール、データ範囲（本人 / 所属組織 / 全体）、匿名利用可否を記載します。未記載の API は脆弱性として扱います。
- 入力の型・長さ・範囲・列挙許可リストを入口で検証します。アップロードの形式・サイズ・保存先を定め、実行可能ディレクトリには保存しません。
- エラーでスタック、SQL、内部 ID を漏らしません。CORS と Content-Type を明示し、利用者コンテンツをエスケープまたは許可リストで清浄化します。
- 秘密情報は環境変数または秘密管理に置き、リポジトリとログに含めません。更新周期と責任者を記載します。具体化は deployment-config-and-secrets に従います。
- 権限変更・エクスポート・削除などを、誰が・いつ・何に・どの前後値で行ったか監査し、保存期間を記載します。
- 依存一覧・バージョン方針と、脆弱性修正を行う担当者・期限を定めます。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| 権限表は API 完成後に追加する | 既定拒否の権限表を先に定めないと全 API の修正が必要になります。 |
| 社内システムにデータ範囲の注記は不要 | 社内にも組織をまたぐ権限逸脱経路があります。 |
| 秘密情報は稼働前に設定ファイルから移す | 一度でもリポジトリやログに入れば漏えいとして更新が必要です。 |
| 監査ログは多いので省略する | 保存期間は調整できますが、機微操作の追跡記録は省けません。 |
| バージョン固定は安全更新を妨げる | 更新担当と期限を含む脆弱性対応方針で解決します。 |

## Red Flags
- API 一覧にロール・データ範囲・匿名可否がありません。
- 認可が抽象的で、ロール→権限→資源の表がありません。
- 詳細エラーを返し、スタック・SQL・内部 ID を秘匿しません。
- アップロードが実行可能領域に保存されるか形式・サイズ上限がありません。
- 設計書・例・リポジトリ・ログに実際の秘密情報があります。
