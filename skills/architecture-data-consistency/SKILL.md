# データモデルと整合性の設計

## Overview
データ層はすべてのモジュールの基盤です。主キー、制約、トランザクション境界、移行手順をアーキテクチャ設計時に確定し、実装と独立したロールバックの根拠を残します。

## When to Use
- データモデル、テーブル定義、移行、並行書き込み、冪等性を設計・レビューするとき。
- 同一トランザクションが必要な操作、結果整合性を許容する操作、ロック方式を判断するとき。
- 対象外：ORM / SQL の実装詳細、オンライン索引再構築の実行、本番の低速クエリ調整。

## Core Process
- 以下の各項目を設計書に明記し、欠落を設計上の不足として扱います。
- 各テーブル・エンティティの主キー方式（連番 / UUID と採用理由）、一意制約、外部キー、カスケード、論理削除と検索への影響を定義します。
- 同一トランザクション内で実行する操作を列挙し、結果整合性を許容する操作には照合・補償タスクと許容遅延を定義します。
- 書き込みは業務一意番号または要求 ID を冪等キーとし、重複要求には初回結果を返します。500 エラーで再試行させません。
- 楽観ロック（バージョン）または悲観ロック（行ロック）、対象、保持時間を指定し、集中更新にはキューまたは分割方式を用意します。
- 移行は nullable 列追加、バックフィル、二重書き込み・読み込み、切替、旧列削除に分割し、各段階を独立して戻せるようにします。大規模変更では影響行数とロックレベルも示します。
- クエリごとに索引の列順と採用理由を記録し、全件走査には条件またはページ上限を設定します。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| トランザクション境界は実装後に調整する | 境界は照合・補償の要否を決め、後から変更すると書き込み経路全体に影響します。 |
| 冪等性は二重クリックが起きてから考える | 再試行・二重送信・タイムアウト再送は通常発生します。初回結果を返す契約が必要です。 |
| 移行は一度で完了した方が簡単 | 一括移行は独立して戻せません。追加から削除までの各段階に戻し方が必要です。 |
| 小規模テーブルの索引は適当でよい | クエリに対応しない索引は書き込みを遅くします。列順と理由を定義します。 |
| 論理削除は deleted_at を追加するだけ | すべての検索の意味が変わるため、既存データの扱いを明記します。 |

## Red Flags
- 主キーの選定理由や業務上の一意キーが不明です。
- 書き込みに冪等キーがない、または重複時に 500 を返します。
- ロック対象・保持時間・集中更新対策がありません。
- 移行が大きな ALTER だけで、段階別の戻し方と影響見積もりがありません。
- 索引がクエリと対応せず、全件走査の上限もありません。
