# コードレビュー項目（提出前の確認）

## Overview
提出前に正しさ、可読性、契約、安全性、性能、テスト品質、コミットのまとまりを確認し、典型的な不具合を防ぎます。

## When to Use
- コードの提出前、受入前の自己確認、他者の変更レビューに使用します。
- 対象外：アーキテクチャ設計レビューと要件レビュー。

## Core Process
- 空、0、負数、極値、重複、過長入力とエラー分岐を処理・テストします。金額は整数または decimal、時刻は UTC を使用します。
- 名前で意図が分かり、関数は 1 画面以内、入れ子は 3 段以内にします。マジックナンバーを定数化し、理解しにくい部分は提出前に整理します。
- 公開関数の引数・戻り値を検証し、エラー型と空値の意味を文書化します。null と undefined を混在させません。
- 全外部入力を検証し、SQL とコマンドはパラメーター化します。ログ・エラーに機微情報を漏らしません。
- ループ内の重複クエリ・計算、N+1 を避け、一括収集して処理します。大量データにはページ分割と上限を設けます。
- テストは例外が出ないことだけでなく具体値を検証し、相互依存をなくし、失敗箇所を特定できるメッセージを付けます。
- 1 コミットは 1 目的とし、理由を記載します。デバッグ出力、コメント化した不要コード、担当不明の TODO を残しません。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| 境界条件は本番でほとんど起きない | 空、0、負数、極値、重複、過長入力の処理とテストは基本条件です。 |
| テストは成功すれば十分 | 具体値を検証しなければ、誤った振る舞いでも成功します。 |
| デバッグ出力や不要コードは後で消す | 主流ブランチへ入り、後続の開発者を誤解させます。 |
| 同時に変更したので大きなコミットでよい | 目的を分けることでレビュー・原因調査・取り消しが可能になります。 |
| 内部関数に契約文書は不要 | エラー型や空値の意味が不明だと呼び出し側が推測することになります。 |

## Red Flags
- 境界・エラー分岐にテストがありません。
- 金額に浮動小数点を使うか、時刻が UTC で統一されていません。
- SQL やコマンドを文字列連結しています。
- ログ・エラーに機微情報があります。
- ループの重複計算・クエリや N+1 があります。
- デバッグ出力、不要コード、担当不明の TODO が混在します。

## Verification
- [ ] 境界とエラーを処理し、テストしています。
- [ ] 名前が明確で、関数 1 画面以内、入れ子 3 段以内、定数化済みです。
- [ ] 公開契約に検証と文書があり、null / undefined の意味が統一されています。
- [ ] 外部入力検証、SQL・コマンドのパラメーター化、機微情報の秘匿を確認しました。
- [ ] テストは独立して具体値を検証し、失敗箇所を特定できます。コミットは 1 目的で理由を記載しています。
