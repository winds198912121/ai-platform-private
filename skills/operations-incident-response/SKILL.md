# 障害対応と振り返り

## Overview
重要度、初動から復旧までの手順、事実の時系列、連絡体制、原因と影響、担当・期限付きの改善とその検証を定義します。

## When to Use
- 本番アラート、主要機能の停止、データリスク、対応組織の立ち上げ、障害の振り返りと改善追跡。
- 対象外：日常の監視設定、公開・戻し方の設計、容量・費用計画。

## Core Process
- P0（中核停止/データリスク）、P1（主要機能低下）、P2（局所異常）に分け、各級の応答時間と通知範囲を示します。
- 影響抑制（戻す/縮退/流量制限）→原因特定（最初に異常となった指標）→最小修正→検証（スモークと指標正常化）の 4 段階で対応します。
- 最初のアラートから復旧まで、誰が・いつ・何を行い・何を観測したかを時系列で記録します。
- 対外通知の担当、更新間隔、経路を決めます。利用者へは影響と復旧見込みを統一して説明し、原因を推測で述べません。
- P0 / P1 は復旧後 48 時間以内に、事実の時系列、技術・手順の根本原因、利用者・データ・金額への影響、担当・期限付き改善を振り返ります。
- 改善を受入まで追跡し、追加監視、回帰ケース、演習記録などの検証証拠を残します。修正宣言だけで完了にしません。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| まず原因の議論を続ける | 先に影響を抑え、その後で特定・最小修正・検証へ進みます。 |
| 復旧すれば記録は不要 | 初回アラートからの行動と観測を追跡します。 |
| 改善案を列挙すれば振り返り完了 | 担当・期限と受入の証拠まで必要です。 |

## Red Flags
- 重要度、応答時間、通知範囲が不明です。
- 推測の原因を告知し、行動・観測の時系列がありません。
- P0/P1 の 48 時間以内の振り返りや、改善の受入証拠がありません。
