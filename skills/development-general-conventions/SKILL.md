# 開発共通規約（実行可能・単体テスト可能）

## Overview
単一責務、登録済み依存、再現可能な振る舞い、明示的なエラー、業務上の意味を持つ名前、単体テストを開発成果物の基本条件とします。

## When to Use
- 開発コードの作成・提出・レビュー、モジュールや関数の規約確認に使用します。
- 対象外：WBS 分解・受入判定（wbs-module-granularity）、見積もり・日程（wbs-estimate-and-dependencies）。

## Core Process
- 1 モジュールは 1 つの責務とし、必要な入口だけを公開し、内部関数は非公開にします。
- 設計書に未登録の依存を導入しません。状態は引数で明示し、グローバルなシングルトンへ隠しません。
- 時刻・乱数・IO は引数または依存注入で受け取り、同じ入力には同じ出力を返します。
- エラーを戻り値または例外の列挙で明示し、握り潰さず、全エラー分岐にテストを設けます。
- 関数は短くし、動詞で命名します。引数は 4 個以内とし、多い場合はオブジェクトにまとめます。
- OrderService / order-service / order_service のように業務上の意味で命名します。M1OrderService.java、m1_order_service.py、E2T1Validate.mjs などの WBS 番号は付けません。M1 / E2 / T3 は内部追跡用です。同一層で重なる場合は OrderRefundService など具体化し、数字を付けません。違反はイベントログに記録されます。
- 正常・境界（空、0、極値、重複）・エラーの具体的な値を検証する単体テストを添付します。
- コメントは処理内容ではなく理由を説明します。TODO には対応条件と責任者を付けます。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| 先にライブラリを導入し、登録は後で行う | 先に設計へ登録し、再現可能なビルドと文書の整合を維持します。 |
| グローバル変数やシングルトンの方が簡単 | 隠れた状態は再現性とテスト独立性を壊します。 |
| 時刻や乱数は直接取得しテストだけ mock にする | 引数注入で同一入力・同一出力を保証します。 |
| エラーは後で処理する | 握り潰すと原因から離れた場所で障害が発生します。明示処理とテストが必要です。 |
| ファイル名の M1 / T2 は WBS 対応に便利 | 番号は内部追跡専用です。成果物では業務上の名前を使います。 |

## Red Flags
- 複数責務のモジュールや不要な公開関数があります。
- 未登録依存、グローバルなシングルトン、隠れた状態があります。
- 時刻・乱数・IO を直接取得しています。
- エラーが catch で握り潰されるか、その分岐にテストがありません。
- ファイル名・クラス名に WBS 番号が含まれます。
- 単体テストがないか、正常系しか検証していません。

## Verification
- [ ] 単一責務、最小公開範囲、同一入力での再現性を確認しました。
- [ ] 依存がすべて設計書に登録され、隠れたグローバル状態がありません。
- [ ] 全エラーが明示され、対応テストがあります。
- [ ] 業務上の名前を使い、WBS 番号がなく、規約違反のログもありません。
- [ ] 正常・境界・エラーの具体的な値を検証するテストがすべて成功します。
