# 公開パイプラインとカナリア配備

## Overview
段階別に失敗で停止するパイプライン、追跡可能な単一成果物、環境差分、配備方式、承認証拠と公開記録を定義します。

## When to Use
- パイプライン、失敗方針、成果物の版と昇格、環境統一、全体・ローリング・Blue/Green・カナリア配備、承認ゲートを設計するとき。
- 対象外：個別リリースの環境表・戻し方・スモーク（deployment-release-and-rollback）、業務コード、CI 構文調査。

## Core Process
- コード取得→依存導入（キャッシュ可）→静的検査・単体テスト→成果物構築→結合テスト→事前環境配備→人の承認→本番の順とし、各段階の失敗で停止します。
- 重複しない SemVer または commit + build 番号を付けます。1 回構築した同一成果物を環境間で昇格させ、環境ごとに再ビルドしません。
- 事前環境と本番のミドルウェア、設定構造、実行引数を揃え、差異を個別登録します。
- 全体、ローリング、Blue/Green、カナリアの方式と、カナリア比率・観測時間を定めます。DB 変更とアプリ公開を分離し、互換性を確保してから切り替えます。
- 承認者、参照するテスト・負荷結果・変更影響、承認記録の保存先を示します。
- 毎回、バージョン、日時、実行者、変更項目、スモーク結果、異常、後続作業を記録します。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| 各環境でビルドし直せば確実 | 同じ成果物を昇格させ、追跡可能性を維持します。 |
| カナリアは少量へ出せばよい | 比率と観測時間、判断証拠が必要です。 |
| 承認はチャットで済ませる | 承認者・証拠・保存先と公開結果を残します。 |

## Red Flags
- 失敗後も次段へ進み、成果物の番号が重複しています。
- 環境ごとの再構築、未登録差分、互換性のない DB と同時公開があります。
- カナリア条件、承認証拠、公開後の結果記録がありません。
