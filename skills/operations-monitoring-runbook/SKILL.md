# 監視と運用手順書

## Overview
トラフィック、エラー、遅延、飽和度の監視と、行動に結び付くアラート、構造化ログ、コマンド付きの調査手順、変更記録を整えます。

## When to Use
- 監視、アラート、ログ、運用手順、調査ツリー、公開・設定変更の記録を設計・レビューするとき。
- 対象外：バックアップ（operations-backup-and-restore）、容量費用（operations-cost-and-capacity）、障害経過と振り返り（operations-incident-response）。

## Core Process
- トラフィック（QPS/同時数）、エラー（率/コード分布）、遅延（P50/P95/P99）、飽和度（CPU/メモリ/接続プール/キュー長）の 4 分類すべてにしきい値と警告レベルを定義します。CPU だけでは不十分です。
- 各アラートに発動条件、影響、最初の対処、復旧しない場合の時間条件とエスカレーション、責任者の役割を記載します。「通知する」だけで済ませません。
- ログは JSON 解析可能な構造化形式にし、要求 ID を経路全体で引き継ぎ、パスワード・トークン・公的識別番号を含めません。
- 運用手順書には日常確認と頻度、復旧時間目標付きのバックアップ・復旧演習、症状から具体的なコマンドへ到達する障害調査ツリーを含めます。
- 公開・設定変更は、誰がいつ何を変え、どう検証し、振り返りが必要か記録します。変更時刻をアラートの時系列と対応させます。
- 監視指標、アラート、ログ、日常確認を相互対応させます。警告対象の指標が画面にあり、手順が参照するログフィールドを実際に検索できることを確認します。

## Common Rationalizations
| よくある説明 | 確認すべき事実 |
|---|---|
| CPU を監視すれば十分 | トラフィック・エラー・遅延・飽和度の 4 種類が必要です。 |
| アラートは担当へ通知すればよい | 最初の行動と、いつ誰へ上げるかを明示します。 |
| 手順はサービス状態を確認すると書く | 実行するコマンドまで具体化します。 |

## Red Flags
- 監視が 1 種類だけで、しきい値・警告レベルがありません。
- アラートに初動・期限・責任者がありません。
- 非構造ログ、要求 ID の欠落、機微情報の記録があります。
- 調査先の指標・ログが存在せず、変更時系列と照合できません。
